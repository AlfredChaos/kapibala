# 00 · 题目总览与考点分析

> 来源：原文题头、§1、§5。【解读】部分为分析推断，非题目规范。

## 一句话

做一个「多账号群组消息平台」的**后端 + 操作控制台**：平台代管若干服务账号、管理若干群，对接一个消息网关和一个 Agent 服务；操作员通过网页控制台管理这一切，并实时看到发生了什么。

## 系统要做的四件事（原文 §1）

1. **账号接入**：把账号连到外部消息网关，并维护账号状态。
2. **消息时间线**：把群里收发的消息记成一条可靠的时间线。
3. **定时序列**：按预设的定时序列，由指定角色的账号往群里发消息。
4. **Agent 自动应答**：接入一个只能通过工具调用交互的 agent，让它能读群消息、发消息、移除成员。

外加一条横切要求：**实时**——操作员在控制台上实时看到发生了什么。

## 技术栈（约定，不可自选）

| 层 | 技术 |
|---|---|
| 后端 | Node.js + TypeScript + PostgreSQL |
| 前端 | React 18 + TypeScript + Vite（UI 库、状态库自选） |
| 外部依赖 ×2 | 消息网关（HTTP + SSE）、Agent 服务（tool use 协议） |

## 关键前提：两个外部服务都要你自己模拟

原文 §1：「系统要对接两个外部服务……它们的接口与行为见第 2 节，**开发和演示时由你自行模拟**。」

【解读】这是审题时最容易低估的一点：

- mock 网关 / mock agent 是**一等交付物**，不是一次性脚手架；
- §2.1 / §2.2 里那些恶劣行为（事件重复推送、乱序、离线补投、504 结果未知、429 计时重置、坏 JSON、未知工具、响应永不返回……）就是 mock 必须内置的**故障开关**——否则 §2.4 的 S1–S8 验收场景无法演示；
- 换言之，**契约即验收基准**：你写的 mock 越贴近 §2 的字面约定，越能自证正确性。

## 交付要求（原文题头 + §5）

- **方式**：GitHub public repo 链接，或含 `.git` 目录的压缩包。
- **内容**：代码仓库（**保留 git 历史**）+ README（说明如何跑起来）。

## 考点分析【解读】

这份题的表层是 CRUD 控制台，内核是**分布式可靠性工程 + LLM Agent 编排**，正好对应「AI 全栈」：

| # | 考点 | 题中的对应 |
|---|---|---|
| 1 | **崩溃一致性**（最重要） | §3 总则「每一条行为，在服务任意时刻重启前后都必须成立」；A2 的出站记录不变量；A5-8 run 恢复；B1 序列重启重排 |
| 2 | **at-least-once 事件流处理** | 网关事件重复 / 乱序（≤1s 窗口）/ 离线补投（不受窗口限制）→ 去重键 `(groupId, msgId)`、排序键 `sentAt` |
| 3 | **状态机建模 + 并发控制** | 账号 6 状态严格转移表、CAS（`expectedFrom`）、终态原子副作用；消息投递 6 状态；群 / run / 序列各有机 |
| 4 | **与不确定性和解** | 504 结果未知 → `unknown` + 5s 判定窗口 + 仅一次重发；audit 拿不到结论 → 3 次重试 → `blocked` |
| 5 | **异步作业编排** | 建群 job（invite 就绪等待 / join 事件确认 / promote 重试上限）；leave-all（群主最后退）；序列链式排期 |
| 6 | **LLM Agent 编排**（AI 部分） | tool loop、12 步 / 60s / 连续 3 次协议错误三重预算、审计门禁、`idempotency_key` 幂等、防御坏响应 |
| 7 | **实时系统** | SSE 入 / WS 出、`seq` 单调、`sinceSeq` 断线补齐、游标分页防重漏 |
| 8 | **认证安全** | refresh 轮换 + 复用检测（整会话作废）+ 前端单飞续期 |
| 9 | **工程交付** | 迁移与 schema 版本检查、统一错误格式、README、git 历史 |

## 48h 打法建议【解读】

优先级原文已给：**A > B > C**，且「做到哪算哪」——这是一场**按完成度与正确性评分**的考试，不是完成全部才有分。

建议的实现顺序（每步都可独立验证）：

1. **项目骨架 + A0**：迁移框架（可重复执行 + schema 版本检查拒绝启动）、统一错误格式、admin/viewer 登录与 403。
2. **mock 网关（最小可用）**：connect / groups / send / events(SSE)，先把"正常路径"跑通；故障开关随后按需加。
3. **A2 入站方向**：SSE 消费 + 游标持久化 + `(groupId,msgId)` 去重 + 时间线落库 + WS 广播（A4 的 seq）。
4. **A1 账号状态机**：转移表 + CAS + 终态原子副作用（这是后面一切的地基）。
5. **A3 建群 job + A2 出站方向**：`queued → accepted → sent/failed`、504 → unknown → 判定 / 单次重发。
6. **A4 分页 + 前端页面 1–3（A6）**：登录、账号列表、群详情时间线。
7. **A5 Agent 编排**：先跑通"正常 agent"（finish/end_turn），再逐个加防御（BAD_JSON / 超时 / 幂等 / 审计 / 恢复）。
8. **B 组**：B3 会话（半小时级）→ B2 leave-all → B1 序列（排期与重启恢复是难点）→ B4 补齐 + 页面 4/5。
9. **C 组**：有余力再做；C2（真实 LLM）对「AI 全栈」岗位的信号价值最高。
