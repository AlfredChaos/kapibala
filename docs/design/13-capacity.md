# 13 · 容量假设与扩容触发器（Capacity Assumptions）

> 本文回答两个问题：**当前架构（单进程 + 单 PostgreSQL，[01](01-architecture.md)）在什么负载假设下成立**；**什么信号出现时才值得引入更重的架构选项**。
> 方法论：**容量从业务推导而来，架构选项跟着触发条件走，不提前实现**——Redis / MQ / 分区 / 缓存 / 多租户全部只出现在 §4 触发器表里，不进当前设计。

## 1. 业务推导链（浓缩）

业务形态：**群控 + AI 销售的控制平面**——终端群成员（外部用户）永远不访问本系统；操作台只被少量运营人员使用。

- 客户群规模 ~100–500，含损耗冗余设计到 1,000–3,000 群（压力点 10,000）；
- 外部反滥用经济学（平台 `FLOOD_WAIT` 即题面 429 计时重置的影子；封号波即 `suspended` 终态 + 自动移出所有群）决定账号池 500–1,000（压力点 3,000）、**月度补充账号是常态**——这正是 A1 终态无出边 + seed 幂等预置的形态；
- `agentEnabled` 默认 `false` → AI 群是少数付费场景，启用群 50–300——agent 并发的天然上限由「每群单飞行」给出。

## 2. 容量预设

| 轴 | 设计点 | 压力点（×3–5） |
|---|---|---|
| 1. 服务账号 | 1,000 | 3,000 |
| 2. 群 | 3,000 | 10,000 |
| 3. 群外部成员 | 50–5,000/群（**不建模**，[02](02-data-model.md) §4.2 / [04](04-group-module.md) §4） | 只影响事件量 |
| 4. 消息摄入 | 10⁵/天（均值 1–2/s，群内突发 50–100/s，**补投风暴瞬时 ×10–50**） | 5×10⁵/天 |
| 5. 出站消息 | ~10⁴/天（受账号限流钳制） | 随账号池线性 |
| 6. Agent runs | 2,000/天，并发 ≤100（每群单飞为天然上限），轮并发受 provider 限制 10–50 | 10⁴/天 |
| 7. 操作台 | DAU < 50，WS 连接 < 20 | 忽略 |

## 3. 逐轴确认：现有设计的匹配情况

**总判断：写路径均值 <100/秒、瓶颈在崩溃正确性而非吞吐——单进程 + 单 PG 成立。** 逐轴：

| 轴 | 确认结论 |
|---|---|
| 1 服务账号 | `account` 3×10³ 行微不足道；限流硬闸门是每次 send 前一次索引点查（[03](03-account-module.md) §5.2），出站 10⁴/天量级下无压力。终态原子副作用单事务、月度补充走幂等 seed——与业务「封号—补充」节奏匹配 |
| 2 群 | `group` / `group_member` 行数 ≤10⁴ + 每群 ≤ 全部服务账号数；`activeAgentRunId` 点查有部分唯一索引支撑（[04](04-group-module.md) §5） |
| 3 外部成员 | **不建成员行**（容量决策已落 [04](04-group-module.md) §4）：契约 `members` 字段只含服务账号、kick 判定查网关列表（[06](06-agent-module.md) §8.5）、agent 触发靠 `ownPlatformUserIds`——三个消费方都不需要外部成员实体。外部成员的存在只体现为事件量与消息行（`sender_platform_user_id` 字符串），随轴 4 一起评估 |
| 4 消息摄入 | 每事件一个小事务（[08](08-realtime-module.md) §1.2）：均值 1–2/s 毫无压力；群内突发 100/s × 单事务 ~2–5ms ≈ 占用单消费者 20–50% 时间，可承受；**补投风暴瞬时 ×10–50（10³–5×10³ 事件/s）是唯一超设计点**——但风暴的本质是**历史回放**（`eventId` 新、`msgId`/`sentAt` 原值），去重键 `(groupId, msgId)` 天然幂等（[05](05-messaging-module.md) §3 / [08](08-realtime-module.md) §1.2 已覆盖，正确性不破，只是吞吐滞后），且网关保留全部历史 → 消费慢了靠 `since` 补拉追上，不丢。应对手段见 §5 微批注记 |
| 5 出站 | ~10⁴/天受账号限流钳制；每账号串行走独立 advisory lock（[05](05-messaging-module.md) §2.2）——1,000 账号 = 1,000 条并行通道，无聚合瓶颈 |
| 6 Agent runs | 2,000→10⁴/天：并发受 `AGENT_MAX_CONCURRENT_RUNS`（默认 50，[06](06-agent-module.md) §2.1）钳制；60s 墙钟 → 理论上限 ≈ 50 × 86400/60 ≈ 7.2×10⁴ run/天 >> 压力点。每群单飞 + 租约观测（[06](06-agent-module.md) §9.4）保证并发不泄漏 |
| 7 操作台 | 忽略 |

**「不引入」的确认**（对应 [01](01-architecture.md) §1 / §9 的取舍）：

- **无 Redis / MQ**：所有异步语义（outbox、死信、事件日志、调度）由 PG 表承载（[10](10-reliability.md) §2）——写路径 <100/s 均值远低于单 PG 舒适区（10³–10⁴/s 事务级），引入外部队列只增加崩溃面；
- **无分区 / 无 K8s**：`message` 年累积 ~10⁷ 行（10⁵/天）仍在 B-tree 索引舒适区；
- **单区域控制平面**：多地域诉求是「团队分布」不是「用户延迟」——终端成员不访问本系统，控制台 <50 人；
- **SSE 单消费者**（[01](01-architecture.md) §5）：单流串行 + 游标连续前缀是正确性最简形态；吞吐不足的拆分条件见 §4 触发器 1。

## 4. 扩容触发器表（出现信号才动手）

| # | 触发信号（可观测） | 动作 | 现有设计留的口子 |
|---|---|---|---|
| 1 | 持续 >500 写/秒（摄入+事件处理+状态写合计）或 timeline 查询 p95 劣化（>200ms） | `message` 按 `(group_id, 月)` 分区；SSE 摄入与事件处理拆独立消费者（按 eventType 或 group 分片） | 事件处理已按「账本 + 死信」解耦（[08](08-realtime-module.md) §1.2），分片只需替换消费循环；分页已 keyset（[05](05-messaging-module.md) §5），分区裁剪友好 |
| 2 | media 累计 >10GB | 本地盘换对象存储（S3/R2） | C1 的 `localFilePath` 是路径字符串（[05](05-messaging-module.md) §7），换 URL 即可；清理逻辑按引用计数已具备 |
| 3 | 账号池 >3,000 或群 >10⁴ | 账号状态热路径（闸门点查）加进程内缓存（TTL + 写穿透失效）；网关连接层（connect/disconnect/SSE 消费）独立成服务 | 闸门判定已收敛在 dispatcher 单点（[03](03-account-module.md) §5.2），缓存只改这一处；连接层边界即 `gateway/` 包（[01](01-architecture.md) §2） |
| 4 | 客户要求独立控制台 / 数据隔离 | 引入多租户（tenant 维度切 account/group/user） | **现在只有 admin/viewer（[09](09-auth-module.md) §4），不提前建 tenant 表**；所有业务表以 `group_id`/`account_id` 聚簇，加 tenant 列的迁移路径清晰 |
| 5 | `gateway_event` 账本累积（10⁴ 群 × 千级外部成员的进出/消息事件 → 年 10⁷–10⁸ 行级） | 按 `event_id` 范围清理（保留窗口，如 30 天）或按月分区 | 账本的去重职责只在「消费进行时」有用（[08](08-realtime-module.md) §1.3 连续前缀只依赖近期 id）；游标远端之后的行可安全清理【注：当前设计无清理，触发前不实现】 |

## 5. 突发与风暴：实现注记

- **补投风暴 = 历史回放**：去重与排序的正确性已在 [08](08-realtime-module.md) §1.2 / [05](05-messaging-module.md) §3 覆盖（去重键幂等、keyset 排序），风暴只影响消费延迟——可接受，追平即可；
- **SSE 微批**（【实现选项，非当前必做】）：把「一个事件一个事务」改为「一个小事务处理 N 个事件（如 N=20 或 50ms 窗口）、游标按批推进」——**保持「游标推进与处理同事务」不变量**（批是事务的粒度，不是不变量的例外）；批内单事件失败时该批退化为逐事件处理（失败的走死信路径，[08](08-realtime-module.md) §1.2 语义不变）。应对 ×10–50 风暴时吞吐可近似线性提升；
- **调度器多实例互斥**：可用 `FOR UPDATE SKIP LOCKED` 替代/配合 advisory lock——已注记于 [01](01-architecture.md) §4.6，此处不重复。
